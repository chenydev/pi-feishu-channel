# 决策记录

每条记录包括：背景、决定、理由，以及被否决的方案。状态为「待定」的条目不阻塞其它工作。

## ADR-1 可选能力保留并插件化

- **状态**：已定
- **背景**：11 项可选能力（定时任务、告警、语音转写、云文档评论、会议邀请、agent 卡片、文档读取、直接执行命令、长回答转文件、会话归档、开通申请）都默认关闭，但它们的接线全部堆在扩展入口里，这是入口膨胀的主要原因。
- **决定**：全部保留，每项做成一个 `BridgeFeature` 模块，由入口按开关装配。
- **否决**：删掉暂时没人用的能力（会丢掉已有测试覆盖的实现）；移到 `experimental/` 目录（只换了位置，没解决接线问题）。

## ADR-2 源码中不写内部编号

- **状态**：已定
- **决定**：注释和测试名里不写 `P1-03` 这类内部工单编号，只写说明；需要追溯时用 `git log` / `git blame`。
- **理由**：外部读者查不到编号对应的内容；而且同一编号在不同计划中指代不同的事，留着会误导。

## ADR-3 配置 schema 用 zod

- **状态**：已定
- **决定**：用 zod 描述配置文件的全部字段，作为字段清单、类型推导、未知字段检测和校验的单一来源（`src/config/schema.ts`）。
- **实施说明**：默认值仍放在 `DEFAULT_CONFIG`，合并与规整（下限收敛、按群覆盖、环境变量优先等）仍由 `loadConfig` 负责；schema 只负责「每个字段的类型和取值是否合法」。这样改动前后同一份配置的加载结果逐字相同（有快照测试锁定），字段集合与 `BridgeConfig` 的一致性由类型层面的检查保证。
- **理由**：配置校验需要的 `.default()`、带字段路径的错误信息，zod 最直接；需要 JSON Schema（例如给编辑器做补全）时，zod v4 也有 `z.toJSONSchema`。
- **否决**：typebox。pi 自身依赖它，但它并不在本包的依赖树里，一样要显式声明；如果借用 pi 的传递依赖，本包就会跟着 pi 的升级节奏走，违背「本地声明保持独立类型检查」的原则（`src/pi-types.ts`）。手写 schema 工具：约 150 行，维护成本高于引入一个成熟库。

## ADR-6 运行时标识更名

- **状态**：已定
- **背景**：项目改名为 `pi-feishu-channel`，但配置目录（`feishu-bridge/`）、环境变量（`FEISHU_BRIDGE_*`）和日志前缀仍然使用旧名。
- **方案**：一并更名，启动时自动迁移旧目录，旧环境变量继续识别一个版本并给出告警（见 [refactor-plan.md](refactor-plan.md) F1）。
- **决定**：采纳上述方案。迁移时在旧位置留软链接，保证会话文件里记录的旧绝对路径和外部脚本仍然有效；新旧目录同时存在时只用新目录，不做合并。
- **影响**：已有部署的环境变量、脚本和文档里的路径需要同步修改（旧名在过渡期内仍可用）。

## ADR-7 审批默认关闭，模式三选一

- **状态**：已定
- **背景**：工具审批原先默认开启（`approval.policyEngine: "bridge"`），没有总开关。只想把通道当聊天入口用的部署，要么一个个工具点「始终批准」，要么把几十个工具名抄进 `approval.autoApprove`，新装的工具第一次调用仍会弹卡。
- **决定**：
  - 字段改为 `approval.mode`，取 `off` / `builtin` / `pi-permission-system`，**不配置 = `off`**，和其它可选能力一样默认关闭；
  - 管理员可以在会话里临时切换（`/feishu approvals <模式>`，只在内存里），`-g` 写回配置文件；
  - 环境变量 `FEISHU_CHANNEL_APPROVAL_MODE` 在判定时读取，不并进配置，`-g` 回写时不会把它冻结进文件；
  - 插件模式的取值直接写插件名 `pi-permission-system`，不用泛称 `plugin`：配置里一眼能看出交给了谁；命令里仍接受中文「插件」；
  - 不兼容旧字段 `policyEngine` 和旧值 `bridge`：当时只有一个部署，直接迁移比维护别名划算。
- **否决**：
  - 保留默认开启、只加一个 `approval.enabled: false`：模式和开关两个字段会出现「关了但模式是 pi-permission-system」这种无意义组合。
  - 从已有配置推断模式（有 `approval` 段就当作想要审批）：规则不直观，删掉一个字段就可能悄悄关掉审批。
  - 会话覆盖落盘：临时设置活过重启，容易忘了它还开着；需要长期生效就用 `-g`。
- **影响**：升级后没有显式配置的部署不再审批；`off` 管不到 pi-permission-system，装了它，它的拒绝照样生效。

## ADR-8 隐式管理员只认归属人和应用管理员

- **状态**：已定
- **背景**：启动时从开放平台查到的应用协作者全部被当作隐式管理员。协作者分管理员、开发者、运营三种角色，开发者和运营能改代码、看数据，不代表能批准工具调用、放行群或绕过私聊白名单。
- **决定**：只认应用归属人和协作者接口里 `type` 为 `administrator` 的人；`type` 缺失或不认识的也不算，并告警。群开通审批的 `owner_collaborators` 随之改为 `owner_admins`。
- **否决**：按角色给不同权限（例如开发者能用管理命令但不能审批）：多一套权限矩阵，实际需求只是「谁算管理员」；需要额外的人时写进 `config.admins`。

## ADR-8 pi-permission-system 的「询问」走它的授权链，不再冒充父会话

- **状态**：已定
- **背景**：要把 pi-permission-system（下称 PS）的「询问」变成飞书审批卡，原先的做法是冒充 PS 的「父会话」：在进程环境里声明父子关系，
  写心跳文件，按 PS 内部的文件格式读请求、写响应（`ps-forwarding.ts`，约 1000 行）。这套文件格式不在 PS 的兼容承诺里，
  代码对齐的是 33.0.3，而 PS 十天内发到了 40.x，其间改过转发请求的形状。PS 27.0.0 起有公开的跨扩展接口：
  按会话发布服务，`registerAuthorizer` 注册授权链环节，带 semver 保证。
- **决定**：
  - 在每个飞书子会话里监听 `permissions:ready`，注册名为 `feishu-channel` 的环节；运维在 PS 配置的 `authorizerChain` 里写上才生效。
    环节按会话的审批模式决定弹卡还是交还 PS，所以会话里临时切换模式也对它生效（原先的转发是进程级的，只跟全局模式）；
  - 最低支持 PS 27.0.0；启动日志、`/feishu doctor` 检查版本和 `authorizerChain`；
  - 环节的放行只管这一次，「本会话批准」「始终批准」由本扩展按 PS 的规则名自己记；
  - 不 import PS 的包，直接读它发布服务的进程级槽位（`Symbol.for("@gotgenes/pi-permission-system:session-services")`）：
    本扩展常以本地路径加载，包名解析不到 PS 的安装目录。槽位名自 27.0.0 起未变；
  - 删除父会话转发和它的配置 `approval.forwarding.*`、环境变量 `FEISHU_PS_FORWARDING`，不做兼容。
- **否决**：
  - 继续用文件转发：每次 PS 升级都可能静默失效，只能靠端到端脚本盯着；
  - 自己实现一套与 PS 同等的规则引擎：bash 复合命令拆解、重定向目标、路径规则都要重做，维护成本远高于接入；
  - fork PS 或给它提 PR 暴露内部协议：PS 发版极快，fork 跟不上；公开接口已经够用，不需要它改。
- **影响**：
  - PS 不允许授权链放行 `path`、`external_directory` 两类请求（读写工作目录以外的文件等），这类请求不再能在飞书卡上批准，
    需要时在 PS 配置里放行。环节对这两类直接交还 PS，不弹一张批了也没用的卡；
  - 飞书会话里由 subagent 发起的询问不弹卡：PS 只让有终端界面的会话应答子会话的询问；
  - 如果将来 PS 提供「无界面会话的人工确认」接口（不受上面那条路径类限制），可以换过去，再把路径类请求也放到卡上。

## ADR-9 自动启动要显式打开，且只在 RPC 模式

- **状态**：已定
- **背景**：扩展装在用户级设置里时，本机每个 pi 进程都会加载它：TUI、`pi -p`、编辑器插件拉起的 RPC 进程。只要读到凭据，
  `session_start` 就自动连飞书，和部署的实例抢同一个应用的长连接（消息可能被本地进程收走）。部署一律是 `pi --mode rpc`，
  pi 的扩展上下文有 `ctx.mode`。
- **决定**：
  - 环境变量 `FEISHU_CHANNEL_ENABLED` 默认关闭，部署的进程显式设 `=1`；
  - 同时要求 `ctx.mode === "rpc"`：开关写进 shell 配置后，本地开 TUI 也不会连。`ctx.mode` 缺失（老版本 pi）时只看开关；
  - 不自动启动时打日志 `feishu.bridge.autostart_skipped`（`reason`：`disabled` / `mode`）、状态栏提示，`/feishu:start` 手动启动不受限制；
  - SIGTERM 处理只在自动启动时挂上，TUI 的信号处理留给 pi。
- **否决**：
  - 只按运行模式判断：编辑器插件等也用 RPC 模式驱动 pi，区分不了部署的进程；
  - 开关放进 `config.json`：配置文件是本机所有 pi 进程共用的，同样区分不了；
  - 开关默认打开（只当关闭手段）：不破坏现有部署，但装到哪台机器上都可能意外连飞书，和「可选能力默认关闭」的约定相反；
  - 按 `ctx.hasUI` 判断：RPC 模式下 `hasUI` 也是 `true`。
- **影响**：现有部署升级前要给进程加 `FEISHU_CHANNEL_ENABLED=1`；在 TUI 或 tmux 里跑 pi 当常驻实例的部署要改成 `--mode rpc`。

## ADR-10 回复机器人的消息免 @ 默认关闭

- **状态**：已定
- **背景**：`groupAlsoOnReply` 原先默认打开：`mention` 策略下，群里有人回复机器人发的消息，不 @ 也会触发一轮。
  群成员常回复机器人的消息和别人讨论，这时并不想叫它，用户会把这当成 bug。而且「是不是机器人的消息」只靠进程内存里最近
  `lastSentCacheSize` 条记录判断，重启后清空，同样的回复有时触发、有时不触发。
- **决定**：默认改为 `false`，需要时用 `config.json` 或 `FEISHU_GROUP_ALSO_ON_REPLY=1` 打开；打开后对整个实例生效。
- **否决**：
  - 保持默认打开：和「可选能力默认关闭」的约定相反，也不符合「群里要 @ 才响应」的预期；
  - 把机器人发过的消息 id 持久化：能让行为稳定，但不解决「不想叫它也被触发」，默认关闭后不值得多一份状态文件。
- **影响**：依赖这个行为的部署升级后要显式打开。

## ADR-11 开通申请扩展到个人，「全局放行此人」用新字段且只放开群

- **状态**：已定
- **背景**：开通申请原先只处理「未放行的群里有人 @」，审批人只能放行整个群。群名单外的人 @、未放行的人私聊都只记日志，
  需要管理员自己去改配置；审批人也没法「只放行这个人，不放行整个群」。
- **决定**：
  - 申请分三种：未放行的群（放行此群 / 全局放行此人）、群名单外的人（加入本群名单 / 全局放行此人）、私聊（放行私聊）；
  - 「全局放行此人」写进新字段 `allowUsersAllGroups`：免掉 `allowChats` 和群名单，仍要 @，群策略 `disabled` / `admin_only` / `blacklist` 照旧，不放开私聊；
  - 群策略拒绝（`group_policy_rejected`）不申请：那是管理员有意设的限制；
  - 频率：同一项申请冷却期内只发一次，「暂不放行」忽略 24 小时，所有申请合计每小时有上限（`accessRequestMaxPerHour`，默认 10）。
- **否决**：
  - 「全局放行」复用 `allowUsers`：它现在只管私聊，改成也放开所有群会让已有配置里的人突然在任何群都能用；
  - 「全局放行」同时放开私聊：私聊只留给归属人、管理员和单独放行的人，审批人要逐个决定；
  - 只按每项冷却限流：有人在多个群里 @、或很多人同时私聊时，审批人仍会被刷屏。
- **影响**：只在开了 `onboarding.accessRequest` 时生效，默认行为不变。

## ADR-12 澄清提问不阻塞会话，作答权限跟准入走

- **状态**：已定
- **背景**：`feishu_ask` 原先在工具里等用户点选项：会话卡在这一轮，期间发的消息要等提问结束才送进去（pi 的 steer 在当前工具结束后才投递）；
  2 分钟没人点就超时，模型自己选默认值接着干；重启后卡片全部失效。作答人写死为管理员（`admins`、应用归属人、应用管理员），
  发起提问的普通成员点不了自己的提问；名单为空时反而谁都能点。
- **决定**：
  - 发出卡片就返回，工具结果带 `terminate: true` 结束本轮；点选项等于以点击人身份往提问所在的会话发一条「[选择] …」消息，走普通消息的排队 / 注入；
  - 作答权限 = 点击人能否在这里 @ 机器人（`admit()` 判定），不另看管理员名单；群里各人会话独立时，答案进提问人的会话；
  - 卡片只防误触：答过一次、同一会话发出新提问、会话重置时失效，兜底 `clarify.ttlMs`（默认 24 小时）；记录落盘，重启后仍能点。
- **否决**：
  - 保持等待，只把超时调长、等待期间暂停空闲计时：会话照样卡住，有提问的会话句柄不能回收，重启仍然丢失；
  - 保持等待，新消息到来时取消等待：模型在一轮中途收到「已取消」，行为不好预料；
  - 作答人 = 发起人 + 管理员：管理员名单是管理权限，不该决定谁能用机器人；群里一起讨论时其他成员也该能回答。
- **影响**：模型不再在同一轮里拿到选择结果，而是在下一轮看到用户的选择；提问失败（卡片和文字都发不出去）时不结束本轮。

## ADR-13 空闲超时分两段，问进度用 /progress

- **状态**：已定
- **背景**：`runIdleTimeoutMs`（10 分钟）对整轮任务统一计时：构建、跑测试这类长时间没有输出的命令很常见，任务经常被误杀。
  任务执行中用户发「做到哪了」：普通消息走 steer，要等当前工具结束才交给模型，期间没有任何回应，交给模型后还会被当成新指令插进任务。
- **决定**：
  - 空闲超时分两段：工具执行中（`tool_execution_start` 到 `end`）按新字段 `runToolIdleTimeoutMs`（默认 60 分钟），等模型时仍按 `runIdleTimeoutMs`；
    中止提示和日志写明卡在哪个工具或在等模型；
  - 新命令 `/progress`：由桥直接回答（运行多久、当前工具及其最近几行输出、待并入和排队数），不经过模型、不打断任务；
  - 工具执行超过 1 分钟时收到普通消息，先回一句正在做什么并提示 `/progress`（同一会话 5 分钟内一次，跟 `queueNotice` 开关）。
- **否决**：
  - 只把 `runIdleTimeoutMs` 调大：模型服务卡住时也要等同样久才发现；
  - 识别「进度」类的自然语言消息自动回答：容易误判，把真正的新指令吞掉；
  - 收到消息就中断当前工具交给模型：会打断正在跑的构建或测试。
- **影响**：默认配置下工具最长可以 60 分钟没有输出；要更早发现卡死的工具，调小 `runToolIdleTimeoutMs`。

## ADR-14 等模型时显示状态，不在桥上自动重试

- **状态**：已定（2026-10-15）
- **背景**：DeepSeek 服务不稳定的一天，用户只看到「正在处理…」：503 被 pi 自动重试接住（单轮最长约 7 分钟才出结果），
  或者请求一直挂住直到 10 分钟空闲超时。DeepSeek 繁忙时先回响应头、再只发 SSE 注释 `: keep-alive` 排队，最长 10 分钟才断开：
  pi 的 `retry.provider.timeoutMs` 只管到响应头，`httpIdleTimeoutMs` 被 keep-alive 重置，都拦不住，pi 也收不到任何事件。
- **决定**：
  - 适配 pi 的 `auto_retry_start` / `auto_retry_end`，重试期间显示状态码和第几次；
  - 等模型阶段 60 秒没有任何事件，提示「可能在排队」并写明多久后自动中止；工具执行中（含等审批，`tool_execution_start` 在审批钩子之前发出）不提示；
  - 状态写在卡片正文末尾和进度消息的状态行，收到输出就消失；文案按分钟取整，进度消息的 20 次编辑上限不会被刷完；
  - 默认开启，不加开关：只是把已有的「正在处理…」说清楚，不改变任务行为。
- **阈值依据**：线上 10-13、10-14 两天 155 轮任务里，排除旧版阻塞式提问后，等模型阶段超过 30 秒的间隔只有 1 次（41 秒），没有超过 60 秒的；
  10-15 故障时 45 秒以上的间隔有 32 次，其中 25 次超过 60 秒。60 秒在正常日子不误报，故障时一分钟内就能提示。
- **否决（暂不做）**：等模型超时后由桥自动重试一次。需要新配置（默认关）和整套开关测试；模型在排队时重试多半还是排队，收益不确定。
  先上线状态提示观察，故障时用户主动 `/retry` 或换模型的比例高，再重新考虑。
- **影响**：故障时用户能看出卡在模型服务，可以自己决定等、`/stop` 还是换模型；运维可按 `feishu.conv.model_retry` / `model_quiet` 统计模型服务的异常频率。

## ADR-15 卡片流式模式被关闭后改用整组件替换，失败说明写进卡片

- **状态**：已定（2026-10-15）
- **背景**：CardKit 的流式模式开启约 10 分钟后被平台关闭，之后 `/content` 返回 `200850` / `300309`。旧实现把它当成普通写失败：
  三次后熔断，卡片停在「正在处理…」或半截内容；长任务的答案降级成另一条文字，空闲超时的中止说明也写不进卡片
  （失败时的「尽力写一句」走的是同一个 `/content`）。用户盯着卡片，看不到另发的文字，以为一直在处理。
- **决定**：
  - 撞到 `200850` / `300309` 时切换为整组件替换 `PUT /cards/{id}/elements/{eid}`，本次写入立即重试，不计入失败；之后正文、页脚、收尾都走它；
  - 卡片模式下任务失败或超时，说明直接写进卡片，写进去就算已交付，不再另发文字；写不进去才走文本通道。
- **否决**：
  - 建卡后定时（如 9 分钟）主动关闭流式模式：多一次调用，提前失去打字机效果；撞到再切换就够了，切换不算失败、本次写入立即重试；
  - 超过 10 分钟就放弃卡片、答案一律发文字：卡片停在半截的问题还在，用户还得往下找答案；
  - 失败时卡片和文字都发：同一句话出现两次，卡片本来就是这一轮的回复。
- **实测**（2026-10-15，真实租户、未发送的卡片）：建卡 10 分 30 秒后 `/content` 依次返回 `200850`、`300309`，整组件替换、`PATCH settings`、全量更新都成功。
- **影响**：超过 10 分钟后卡片没有打字机效果（整段替换）。整组件替换是卡片写入的第二条路径，假服务同步模拟了这条平台行为。

## ADR-16 群聊默认全群共用一个会话，切换后能找回个人会话

- **状态**：已定（2026-10-15）
- **背景**：`groupSessionsPerUser` 从第一版起默认 `true`（沿用 hermes 的群内按人隔离）。实际用法是一个群围绕一件事协作：
  A 让机器人做的事，B 接着追问时机器人不知道上下文，只能让 B 改去话题里问，或者重新交代一遍。
- **决定**：
  - 默认改为 `false`，群普通消息的会话键是 `<chatId>`，全群共用；话题仍按话题共用，私聊不变。
    共用会话里 `agentContext.sender: shared` 会给每条消息加发言人，模型分得清谁在说话；
  - 切换后找回个人会话：群里的 `/sessions` 接着列出本群旧的 `<chatId>:u:*` 指针里的会话，`/resume` 把群会话指针指过去，工作区一起带过来。
    只有本人或管理员能恢复：恢复后全群都能看到这段上下文，包括群里看不到的工具输出和读过的文件。
- **否决**：
  - 保持默认按人隔离、靠文档引导开启共享：多数群要先踩一次「机器人不记得别人说过什么」才知道去改配置；
  - 升级时自动把某个人的会话并进群会话：选谁都不对，多人的会话也没法合并成一段；
  - 按群设置 `sessionsPerUser`：先看找回个人会话够不够用。
- **影响**：升级后没显式写 `groupSessionsPerUser` 的群从新的共享会话开始，旧的个人会话要手动 `/resume`；
  共用会话里任何能用机器人的人发 `/new`、切模型都会影响全群。

## ADR-17 用量默认不绑厂商，进度默认只在换工具时加行

- **状态**：已定（2026-10-15）
- **背景**：两个默认值是按自己的用法定的，不适合公开的通用扩展：
  - `usage.provider` 默认 `deepseek`：没用 DeepSeek 的人也会去查它的余额，页脚按它的价表折算人民币；
  - `progress.mode` 默认 `all`：每次工具调用加一行，群里全群共用会话后（ADR-16）所有人都看得到，太吵。
- **决定**：`usage.provider` 默认 `none`，未知取值也按 `none` 处理；`progress.mode` 默认 `new`。
- **否决**：顺带把 `approval.mode` 默认改为 `builtin`：维持 ADR-7「审批默认关闭」，靠 `allowChats` / `allowUsers` 默认拒绝兜底。
- **影响**：用 DeepSeek 的要显式写 `usage.provider: "deepseek"`，否则页脚没有人民币、`/feishu usage` 查不到余额；
  要每次工具调用一行的写 `progress.mode: "all"`。

## ADR-18 运行中重新读取配置，只应用用到时才读的字段

- **状态**：已定（2026-10-15）
- **背景**：配置只在启动时读一次，改任何字段都要重启；重启会打断正在跑的任务，多人在用的实例很难找到空档。
  而组件拿配置的方式不一样：准入、展示、会话路由每次都从 `rt.config` 读；超时、缓存容量、定时器间隔在构造组件时传进去；
  可选能力插件按开关决定装不装。
- **决定**：加 `/feishu config reload`，重新读取文件后只把「用到时才读」的字段原地写进 `rt.config`。
  每个字段在 `src/config/reload.ts` 的 `RELOAD_RULES` 里归为 `live` / `restart` / `runtime`，类型上要求顶层字段和对象子字段都归类，漏了编译不过；
  `docs/configuration.md` 的「改后」列由它生成。合并窗口 `batch.textWindowMs` 改成每次重新读取，归为 `live`。
- **否决**：
  - 全部字段都写进内存，回执里提示哪些要重启：构造时取值的组件还在用旧值，内存里却是新值，`/feishu doctor`、`/feishu status` 看到的和实际行为对不上；
  - 重建组件（重新装配会话管理器、重连长连接）让所有字段都能热加载：等于进程内重启，进行中的任务和审批卡的状态要迁移，复杂度和风险都比重启高；
  - 监听文件变化自动重新读取：编辑到一半的文件会被读进去，改动什么时候生效也不可控。
- **影响**：新增配置字段时必须决定它能不能热加载。归为 `live` 的字段，读取处不能在构造时缓存它的值。
